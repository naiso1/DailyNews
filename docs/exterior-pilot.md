# 外装ニュース：試用とヒアリング

## 初期設定

- 内装の既存URLを維持し、外装は `http://IEWEB01/exterior/` に公開。
- 対象はグリル・バンパー・外装加飾・エンブレム・発光・センサー透過・ウェザーストリップ等。地域は日本・中国・インド・米国・欧州。
- 2026-09-16から「製品・技術」と「トレンド・マーケット」を区分する。トレンドはデザイン、市場、規制、材料、競合に分類する。1号あたり各地域10件、計50件を目標とし、製品6件・トレンド4件を目安にする。一方の不足分は他方の適格記事で補い、トレンド4件を固定上限にはしない。
- 号の対象日の記事を優先し、不足する地域は当日を含む直近7日の未掲載記事から補う。検討候補は1地域最大60件。記事の元公開日と掲載する号の日付は分ける。製品60点以上・トレンド65点以上の関連性基準を保ち、対象外・低得点・同一発表の重複・別の号の既掲載記事で10件を埋めない。適格記事が足りない場合は10件未満とする。
- カードは内装版と同じ構成とし、分類・「直近7日から補充」の追加帯は表示しない。区分による絞り込みと元公開日の表示を維持し、ヘッダーは号の日付と件数を表示する。
- 地域は媒体の分類であり、発売市場・採用地域と同義ではない。市場の対象範囲、発表と予測、開発車と市販仕様、過去事例の再紹介を本文に従って区別する。取得成功で該当なしの号と、取得失敗も区別する。
- 各地域の掲載記事から考察と2件ずつの企画例を作る。事実と自社の仮説を分け、全案に出典IDと具体的な評価方法を付ける。根拠がない地域は情報不足を明示する。
- 外装へのアクセス数、記事閲覧、いいね、コメント、お気に入りは内装から独立。ログインID・パスワードは共通とし、メール購読は版ごとに管理する。
- 社内ネットワークから外装URLを開くだけで閲覧可能。内装に登録済みの方は同じメールアドレス・パスワードでログインする。外装からの新規登録は両版の受信チェックが初期オフ。登録画面またはマイページで内装だけ・外装だけ・両方・受信なしを選択できる。
- メールは月～金の朝8時に配信。購読変更は2分間隔で宛先JSONへ同期し、通常は次回同期まで最長約2分で反映する。OneDrive同期時間も加わるため、8時直前の変更は当日の配信に間に合わない場合がある。
- 初期配信先は私有の名簿に登録した管理者1名。氏名・メールアドレス・認証値は設定ファイルやGitへ追加しない。
- 元記事の写真は利用し、AIによる企画画像はexaBaseで生成する。自動生成は最新号の各地域2案、既存画像を含めて最大10枚を上限とし、外装では有料画像APIへの代替呼び出しを行わない。画像ごとに生成元を表示する。内装は次号からexaBaseを優先し、失敗案だけ既存Gemini APIへ代替する。

## メンバーへのヒアリング（1週間程度の試用後）

### 初回の内容確認で残した課題

初回は収集対象日2026-09-14の枠に2記事を採用し、2地域の考察と4案を作成した。材料の帰属、出典リンク、事実と仮説の区別を校正済み。

初回収集ではRSSのUTC日付と日本時間の掲載日が異なる場合があった。2026-09-16の改善で外装の日時を日本時間へ正規化し、日付の境界を検索範囲にも反映した。既存の掲載済み記事の日付や内装の処理は一括変更しないため、過去分には従来の収集日が残る。

同日の当日記事だけの再評価では9月15日公開の記事を21件へ増やした。その後、各地域10件を目標に、直近7日から未掲載記事を補う運用へ見直した。例えば9月15日号では9月9日〜15日公開の記事を対象にできるが、9月10日の記事を9月15日公開と書き換えない。関連記事の再配信や更新日時だけが新しい記事を、新規記事として重複計上しない。

### 確認する質問

1. 業務で役立った記事を3件、不要だった記事を3件。それぞれ理由は何か。
2. もっと知りたい製品・技術・企業・地域は何か。対象から外すものは何か。
3. 要約に足りない情報は何か。構造、材料、工程、性能、採用車種など、優先する項目は何か。
4. 各地域の考察・2件の企画例は実務に役立つか。出典、仮説、評価方法のどこを改善したいか。
5. メールの頻度・時刻・分量は適切か。毎日／週次のどちらがよいか。
6. 検索・フィルター・お気に入りなどで困った操作はあるか。

キーワードだけでなく具体的な記事URLと理由を集め、`editions/exterior/settings.json` とプロンプトへ反映する。個別メンバーの回答や名簿は公開コンテンツに含めない。

## 公開・配信の確認

- 内装を見たあと外装を開いても、それぞれの訪問が計上される。
- 外装URLをメール購読なしで閲覧できる。共通アカウントのマイページで内装・外装を個別に選択し、受信オンで追加・オフで解除される。別の画面で設定が変わった場合は最新値を確認してから保存する。
- 購読変更後、次回の2分周期の同期とOneDrive同期を経て宛先JSONへ反映される。処理PC停止やサインアウト時には反映が遅れることも確認する。
- 外装の更新失敗が内装の成功判定や名簿を書き換えない。
- 処理の実行日、号の対象日、記事の元公開日、公開確認、メール送信成功、実受信を別々に確認する。
- 各地域の号内件数、直近7日からの補充件数、重複除外、考察と2案の出典IDを確認する。元記事の日付で表示しつつ、号ごとの一覧に補充記事が含まれることを確認する。
- 朝8時のフローが外装の宛先JSONを読むこと、内装の名簿を参照しないことを確認する。配信直前の購読変更は当日分へ反映されない場合がある。

## exaBase画像生成の実機確認

共有の軽量版1.1.4エンジンを利用し、1企画から1プロンプトを作り、画像と企画ID・出典IDを対応づける。2026-09-16に専用セッションでの認証と、2026-09-15号の5地域各2枚、計10枚をexaBaseで実生成・目視確認済み。企画ID5〜8の既存4枚を保持し、欧州・中国・インドの企画ID9〜14の6枚を追加した。ID10は内容確認後に再生成し、最終画像を採用した。今回の追加生成に画像APIは使用していない。定時生成は `enabled: true, provider: "exabase"`、最新号の各地域2案、既存画像を含めて最大10枚を対象とする。

- 専用Edgeコンテキストに処理PCのWindowsユーザーが初回ログインし、認証状態をDPAPIで暗号化保存する。他ユーザー・既存共有ツールの認証状態は転用しない。
- タイムアウトと完了キャッシュを備え、送信後に結果不明となったジョブは自動再送しない。画像失敗時も文章の公開と通知を止めない。
- 既に画像のある案は再生成せず、過去号の未生成案へは遡らない。画面上は生成元に応じて「AI生成イメージ（exaBase）」または「AI生成イメージ（API）」と表示する。出自が確認できない旧画像には生成元を推測で付けない。
- 参照画像対応は別途検証。現行軽量エンジンには添付画像引数がなく、企画文と元記事のタイトル・要約を参照する。

内装は2026-09-15より後の最新号からexaBaseを優先し、失敗した案だけ既存Gemini APIへ代替する。既存の内装画像は保持する。設定とモック検証を完了しており、内装の新規実生成は次回の定時処理で確認する。初回ログイン、1案の確認、再実行、定時処理と代替処理の設定は[exaBase連携の運用手順](../deployment/workstation/exabase/README.md)を参照。
